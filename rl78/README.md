# RL78 命令シミュレータ・コア

ルネサス RL78（S1 / S2 / S3 コア）の命令シミュレータ。C11、外部依存なし。
一次資料は「RL78 ファミリ ユーザーズマニュアル ソフトウェア編」R01US0015 Rev.2.40。
乗除算器 SFR は RL78/G13 ハードウェアマニュアル R01UH0146 第 14 章に基づく。

## ビルドとテスト

```
sh rl78/tests/run_tests.sh          # macOS / Linux（CC で変更可。既定 cc）
rl78\tests\run_tests.bat            # Windows（clang / LLVM）
```

全テスト・ベンチをビルドして走らせ、件数と失敗数を表示する。失敗があれば非 0 で終わる（0 件も失敗）。
環境変数 `BENCH_MIN`（百万命令/秒）を与えると、ベンチマークがそれを下回ったときに失敗にする。
コンパイルには `-fno-unroll-loops` を付ける（clang 20 の x86-64 では、付けないと命令実行ループが約 10 倍遅くなる）。
`RL78_GNU_BIN` に GNU の rl78-elf-* ツールのディレクトリを入れると、差分テスト（下記）も走る。

## 公開 API（`include/rl78.h`）

- 生成: `rl78_default_config` / `rl78_create` / `rl78_destroy`。`rl78_config` でコア種別
  （S1 / S2 / S3 と、品種不明時の上位互換 `RL78_CORE_AUTO` = S3 の命令と G13 乗除算器 SFR の両方。
  MACH/MACHU による MACR（FFFF0H〜、MDAL/MDAH と同じ番地）の更新では乗算器は動かない）、
  コードフラッシュ容量（書き込み無視・フラッシュ読みのクロック）、データフラッシュ範囲、ミラー領域
  （開始・終了・転送元。PMC.MAA で +10000H）、G13 乗除算器の有無、HALT/STOP 時の挙動、割り込み受付クロック。
- メモリ: `rl78_load`（イメージ書き込み）、`rl78_peek8/peek`（副作用なし）、`rl78_read8/16`、
  `rl78_write8/16`（フック・SFR の動作つき）、`rl78_memory`。
- レジスタ: `rl78_get_reg/set_reg`（X..H, AX..HL, PC, SP, PSW, ES, CS, PMC）、`rl78_get_bank_reg/set_bank_reg`。
  PC を設定すると HALT/STOP 状態も解ける。
- 実行: `rl78_reset`（リセットベクタから）、`rl78_run(cpu, 最大命令数)` → 停止理由
  （上限 / ブレーク / HALT / STOP / 未定義命令 / 停止要求）、`rl78_step`、`rl78_request_stop`、
  `rl78_insn_count` / `rl78_clock_count` / `rl78_clear_counters` / `rl78_add_clocks`、`rl78_last_fault`。
- ブレーク: `rl78_add_breakpoint` / `rl78_remove_breakpoint` / `rl78_clear_breakpoints` / `rl78_breakpoint_count`（個数の上限なし。ビットマップを初回に確保）。
  別の 1 MB のトラップマスクを先頭オペコードのフェッチ時だけ OR する。メモリを書き換えず、
  フェッチ・データ読み出しにブレーク有無の分岐を追加しない。ミラー・ES:・直接参照でも元のバイトが見える。ブレーク位置から実行を始めるとその命令を実行する。
- 割り込み: `rl78_request_interrupt(cpu, ベクタ番地, 優先度)` は保留され、IE=1 かつ優先度 ≤ ISP のとき
  命令の境界で受け付ける（PSW・PC 退避、IE=0、ISP=max(優先度-1,0)、割り込み保留命令の次の 1 命令後）。
  保留中の要求は HALT/STOP を解除する。`rl78_force_interrupt`、`rl78_cancel_interrupts`。
- フック: `rl78_add_hook(cpu, 開始, 終了, read, write, ctx)`。フックのない領域は配列直接の高速経路。
- スナップショット: `rl78_snapshot_create/update/restore/free`（メモリ・レジスタ・保留割り込みに加えて
  命令数・クロック数のカウンタも戻る。ブレークとフックは含まない）。
- 逆アセンブル: `rl78_disasm_buf` / `rl78_disasm`（マニュアル表記。saddr は 4 桁、sfr は 5 桁か名前）。

## C への変換（`src/rl78_xlate.c`）

コードフラッシュの機械語を C に変換し、clang でコンパイルしたものを実行する方式。解釈実行より数倍速い
（試作での測定: Windows の CI で 2.7〜3.0 倍、Linux で 3.3〜3.4 倍、arm64 の Mac で 4.2〜4.9 倍）。
解釈実行はそのまま残り、変換したコードがない場所は自動的に解釈実行になる。結果は同じ。

- 変換後の C は、1 命令につき `rl78_xl_exec1()` の呼び出し 1 つ。引数は番地と命令バイト（定数）。
  `rl78_xl_exec1()` の中身は解釈実行と同じ命令の `switch`（`rl78_exec_ops.inc`）で、コンパイラが定数に合わせて
  該当の命令だけに畳み込み、命令をまたいで最適化する。命令ごとの動作を書き直していないので、解釈実行と食い違わない。
- **関数の呼び出し**: 変換済みの関数への `CALL` は、いったん外（表を引いて次の関数を呼ぶ処理）へ戻らずに、
  その場で相手を実行する。外へ戻ると、呼び出しと復帰のたびに表の検索・関数ポインタ経由の呼び出し・入口の
  `switch` がかかり、数命令ごとに小さな関数を呼ぶコードでは実行時間の大半がそれになるため。
  - RL78 の関数 1 つは、C の関数 2 つになる。本体 `xl_iNNNNN`（CPU の状態を値で受け取って値で返す）と、
    外から呼ぶ `rl78_xl_fNNNNN`（CPU から状態を読み、本体を呼び、書き戻す）。
  - 同じ C ファイルの関数は本体を直接呼ぶ。状態を CPU に書いて読み直す手間がない。
  - 命令が 24 個以下で `CALL` を含まない関数は、呼び出し元に埋め込む（`always_inline`）。別の C ファイルの関数でも、
    その条件に合えば本体の写しを呼び出し元のファイルに置いて埋め込む（C ファイルは番地で区切るので、
    実際のコードの呼び出しの多くはファイルをまたぐ）。
  - それ以外の別ファイルの関数は `rl78_xl_fNNNNN` を呼ぶ（状態は CPU 経由）。
  - 埋め込まない呼び出しは、RL78 の呼び出しの深さ 32 段（`RL78_XL_MAX_DEPTH`）まで。それより深い呼び出しと
    戻ってこない再帰は今までどおり外へ戻るので、ホストのスタックは増え続けない。
  - 同じ関数の中への呼び出し（再帰など）は、今までどおり同じ C 関数の中の分岐になる。
  - 呼ばれた側が入口で命令数の上限とブレークポイントを確かめるのは同じなので、止まる命令は解釈実行と変わらない。
- RL78 の関数 1 つが C の関数 1 組。関数の入口から到達できる命令をたどって集める。ブロックの先頭（分岐先、
  CALL の戻り先など）だけが入口になり、そこで「残りの命令数がブロックより少ない」「ブレークポイントがある」ときは
  解釈実行に渡す。だから `rl78_run()` の命令数の上限やブレークポイントは、解釈実行と同じ命令で止まる。
- 長い関数（200 命令を超えるもの。`XL_PART_INSNS`）は、番地の順に区切って複数の C の関数に分けて書く。
  C コンパイラは 1 つの関数が長いほど、長さの割合以上に時間がかかる（3400 命令の関数 1 つで 1 分。分けると 15 秒）。
  区切りをまたぐ分岐は、その C の関数をいったん出て、行き先のある区切りに入り直す（止まる命令は変わらない）。
  ループの途中では区切らない（どこで区切ってもループの中になるときは、またぐ後ろ向きの分岐が一番少ない所で区切る）。
- C の関数の中では、行き先を調べ直さない。知らない番地（その C の関数のブロックの先頭ではない番地）へ飛んだら
  その C の関数を出て、呼んだ側（呼び出し元、最後は振り分け役）が続きを決める。以前は関数の中に調べ直しの `switch` が
  あり、C の関数全体が 1 つのループになっていた。clang 18 は、関数によってはそのループの最適化（LICM）に数分かけた
  （利用者のプログラムで、1 ファイル 360 秒のうち 280 秒）。
  - 代わりに、再帰する関数の `RET`（戻り先が同じ関数の中）は振り分け役を通るので、再帰の多いコードは遅くなる
    （arm64 の Mac、再帰が中心の測定用プログラムで毎秒 12.5 億 → 7.0 億命令。再帰のない呼び出しの連なりでは変わらない）。
- 制御の流れの解析（逆アセンブル結果から分岐先を拾う）はヒントでしかない。間違っていても遅くなるだけで、
  結果は変わらない（知らない番地へ飛んだら、その C の関数を出て、変換済みの別の関数か解釈実行に移る）。
- ブロックの途中にブレークポイントを置くと、その間は変換したコードを使わない。
- 関数の中で前へ進む分岐（条件分岐の飛び先、分岐しなかった側、スキップ命令の先）は、飛び先のブロックの確認を通らない。
  手前の確認が、次の確認までの一番長い道のり（64 命令まで。`XL_FREE_MAX`）を命令数の上限と比べてあるからで、
  止まる命令は解釈実行と変わらない。確認が残るのは、関数の入口、後ろへ戻る分岐の飛び先（ループは 1 周に 1 回）、
  `CALL` の戻り先、行き先を調べ直して入るとき。
  - 上限の近くでは、今までより少し手前（最大 64 命令）から解釈実行に渡す。
  - 確認を通らずに入れるブロックの先頭に置いたブレークポイントは、「ブロックの途中」と同じ扱いになる
    （その間は変換したコードを使わない）。関数の入口のブレークポイントは今までどおり、変換したコードを使ったまま止まる。
  - 分岐の多いコードで効く（arm64 の Mac、関数を呼ばないループで 1.16 倍。関数の呼び出しが多いループでは変わらない）。
- どの関数を変換するかは、CALL の飛び先の記録（`rl78_set_call_profile`）から決められる。
- 変換したコードは C ライブラリなしでコンパイルできる（`<stdint.h>` / `<stddef.h>` だけ）。Windows では
  LLVM の配布物の clang と lld-link だけで DLL にでき、Windows SDK は要らない。
- gcc ではコンパイルできない（インライン展開の途中で `switch` を刈り込まないので、終わらない）。
- `rom_size` が 0（コードフラッシュを書き込み禁止にしていない）の CPU には取り付けられない。
- 番地が定数の RAM の読み書き（`!addr16`、saddr など）は、ページの表（`rp` / `wp`）を引かずにメモリを直接読み書きする。
  表の中身はコンパイラから見えない（どのバイトの書き込みでも変わりうる）ので、引くたびに読み込みと分岐が要り、
  その先の遅い経路のために CPU の状態をすべて書き出せる形に保つ必要があるため。対象は「固定 SFR の手前まで続く、
  素のページ（読み書きがメモリそのもの）の並び」（`rl78_xl_plain_range`。RAM、saddr、レジスタバンク）で、変換のときに
  コードに埋め込む。ミラー、コードフラッシュ、フックのあるページは入らない。取り付けるときにこの範囲が素のままか確かめ、
  あとでフックなどで変わったら、その間は変換したコードを使わない（解釈実行になる）。

テストは `tests/xlgen.c`（変換）→ clang で DLL →`tests/xlrun.c`（解釈実行との照合）。`run_tests.sh` / `run_tests.bat` が通す。
clang は環境変数 `XLCC` で指定できる。

### GNU シミュレータとの差分テスト（`tests/difftest/`）

binutils 2.43.1 の as/ld/objdump と GDB 15.2 の rl78-elf-run を実行するだけで、コードは写していない。
同じバイナリを両方で走らせ、レジスタ・PSW・SP・ES/CS・関連メモリを比較し、逆アセンブルを
objdump と比較する。説明のつかない食い違いが 1 件でもあれば失敗。以下はマニュアルを正として
GNU 側の誤り（または未規定）と判断した既知の差：

- AC: GNU は下位ニブルの大小で近似しており、マニュアル 6.3 の「ビット 3 と 4 の間の桁上がり/借り」と異なる
- CMPS の CY（マニュアル: 結果が 0 以外、または A か X が 0 なら 1）
- ADDW SP,#byte / SUBW SP,#byte で GNU は PSW を変える（マニュアル: 不変）
- PUSH/POP PSW の 2 バイトの順序が GNU は逆（マニュアル図 3-5: SP-1 に PSW、SP-2 に 00H）
- CALL/CALLT: マニュアル図 3-5 は SP-1 に 00H を書くが GNU は書かない
- ES/CS の上位 4 ビット、SP のビット 0、S1 の RBS ビットを GNU はマスクしない
- MACH/MACHU: GNU は MACR を誤って読む（手計算で本コアの値が正しいことを確認）
- CALLT: GNU は表を F00xxH から読む／BRK と HALT/STOP で GNU は終了する／FFFF8H より上への 16 ビット書き込みと奇数番地の 16 ビットアクセスで GNU は異常終了する（いずれも比較対象から除外）
- クロック: GNU は ES: の +1、フラッシュ読みの加算、EI/DI・MOV PSW・RETI などの値がマニュアルと違う（本コアの値は manual スイートで表と照合済み）

## 裏が取れていない点（実機や Renesas 製シミュレータとは未照合）

- DEC の AC: マニュアルの文言（ビット 3 から 4 への桁上がり）は減算では起こらない。ビット 4 からの借り（下位ニブルが 0 のとき 1）と解釈した
- ADDW/SUBW/CMPW の AC はマニュアルで不定。ビット 3/4 間の桁上がり・借りを返している
- CALL/CALLT の SP-1 への 00H 書き込み（図 3-5 に従ったが、操作一覧には記載がない）
- 奇数番地への 16 ビットアクセスはビット 0 を 0 にして扱う（表 5-1 注 1 を全 16 ビットアクセスに適用）
- 未定義として止めるもの: 命令マップの灰色セル（例 `21`、`31 x7`〜`31 xF` のシフト数 0、`61 81`・`61 A1`
  などの 2nd MAP 1 列目 8〜F 行、`61 88`）と、表 5-8 に ES: 形式のない命令に付いた ES:（例 `11 00`）。
  objdump はこれらを `add a,[hl+b]`、`xch a,x`、`nop` などと読むが、マニュアル上は定義がないため実機の動作は不明。
  `FF` は実機では不正命令による内部リセット。本コアは `RL78_STOP_UNDEFINED` とし、
  `rl78_last_fault` に FFH と内部リセットの専用説明を返す（PC・命令数は実行前のまま）。
- 割り込みの受付条件（優先度 ≤ ISP、受付後 ISP=優先度-1）は G13 ハードウェアマニュアル 16.3.5 による。受付に 9 クロック（設定可）
- G13 乗除算器: 8 ビット書き込みでも積を再計算する、MACOF は直近の積和で更新、除算は即時完了（DIVST はすぐ 0）、0 除算の結果は未定義のため商 FFFFFFFFH・余り＝被除数とした
- 計測していないクロック要因: RAM からの命令フェッチ（7.2.2）、パイプラインハザード（7.2.3）
- 割り込み要求フラグ・マスク SFR への書き込みによる割り込み保留（周辺機能扱いのため対象外）
